# Contract - badbatch

This contract is the executable spec for badbatch. Every obligation below is stated so it can fail. The full contract is the first build act of this repo and it extends the stub obligations written here.

## Stub obligations

BB-S1. Every stamped artifact carries the agent, the prompt hash, and the model that made it, and a stamp missing any of those fields is rejected rather than stored incomplete.

BB-S2. A recall walk from any stamped artifact lists every downstream artifact derived from it, and an artifact reachable through the stamp graph but missing from the walk is a defect the tests must catch.

BB-S3. Every artifact in a recall result is sorted into exactly one reversibility class, reversible, reversible with compensation, or irreversible, and an unclassified artifact in the result is a defect.

BB-S4. The recall walk reports only and changes nothing, and executing a recall is a separate act that never happens as a side effect of walking the graph.

BB-S5. Every fixture and example in this repo is synthetic and built for this repo, and no real trace or session data appears anywhere in the tree.

## Round 1 obligations

Round 1 builds stamping for the files in one repo plus the recall walk, over recorded files only. A run record is the recorded text one run left behind about its own work in one repo. A stamp is the document the tool prints for one run record. A current state is a recorded list of the digests the paths in the repo carry now. The tool reads the files it is handed and prints documents, and it writes nothing into any repo it describes. No decision model is called in this round, and stamping and the walk are deterministic rules with no judgment in them, because the decision points the roadmap names belong to recall execution planning in a later round.

A meaningful line is a line that is neither blank nor a comment, and a comment line is a line whose first character that is not a space is the hash character. A run record opens with a header of four meaningful lines in this order, naming the run, the agent, the prompt hash, and the model. After the header come file entries and artifact entries in any order. A file entry names one path and one action, created, modified, or deleted, and a created or modified entry is followed at once by a content block, which is the word content on its own line, then the recorded post-run content lines exactly as recorded, then the word end on its own line. Inside a content block every line is literal content, blank lines and comment lines included, and a content line that reads exactly end closes the block, so that one line can never appear inside recorded content. A deleted entry carries no content block. An artifact entry names one path, the paths it derives from written after the words derived-from as a comma separated list, and its reversibility class written after the word class, and it is followed at once by a content block in the same shape. A path is one token with no spaces, never absolute, and never carrying a parent reference. The values on the header lines are one token each.

The digest of recorded content is the SHA-256 digest, written as sixty-four lowercase hex characters, of the UTF-8 encoding of the content lines with one newline character after each line, so content with no lines digests the empty string. The reversibility classes are named reversible, reversible-with-compensation, and irreversible, and their sort order in a recall result is the order named here, reversible first and irreversible last. Where one artifact derives from a stamped file by more than one path, the chain the walk prints is a shortest path, and ties between shortest paths are broken by the lexicographically smallest sequence of paths.

The formats in brief are shown here once, and the obligations below state them as rules that can fail.

```
run run-0007
agent writer-3
prompt-hash b41d90
model synth-writer-2

file src/report.py created
content
print("report")
end

file src/legacy.py deleted

artifact build/report.html derived-from src/report.py class reversible
content
<html>report</html>
end
```

```
stamp run-0007
agent writer-3
prompt-hash b41d90
model synth-writer-2
file src/legacy.py deleted none
file src/report.py created DIGEST
artifact build/report.html reversible DIGEST derived-from src/report.py
```

```
recall src/report.py
artifact build/report.html reversible current chain src/report.py -> build/report.html
```

BB-1. A run record parses only when its first four meaningful lines are the header lines in the order run, agent, prompt-hash, and model, each naming exactly one value, and a record missing any of those four fields, naming one of them twice, or opening with any other meaningful line is refused rather than stamped incomplete.

BB-2. A malformed run record is refused with an error that names the source and the defect, and the refusal covers a meaningful line that matches no entry form, a file entry whose action is not created, modified, or deleted, a created or modified file entry with no content block after it, a deleted file entry carrying a content block, a content block that reaches the end of the record with no closing end line, a duplicate file path, a duplicate artifact path, an artifact path that equals a file path, a path that is absolute or carries a parent reference, an artifact entry with an empty derivation list, an artifact whose derivation names a path the record never declares as a file or as an artifact, an artifact that derives from itself directly or through a chain of artifacts, and an artifact entry with no class or with a class outside the three named classes, and no refusal ever surfaces as a traceback or as a partial stamp.

BB-3. The stamp for one run record prints the stamp line naming the run, then the agent, the prompt hash, and the model from the record header, then one file line per touched file sorted by path, naming the path, the action, and the digest of its recorded content, with the word none in place of a digest for a deleted file, then one artifact line per declared artifact sorted by path, naming the path, its class, the digest of its recorded content, and its derivation parents sorted by path, and the stamp declares no file, no artifact, and no derivation link the record does not declare.

BB-4. The content digest is computed by the rule stated above and by no other rule, and the same recorded content carried under two different paths produces the same digest in both stamp lines, and recorded content differing in any one line produces a different digest, and every digest printed in a stamp is sixty-four lowercase hex characters.

BB-5. A stamp document parses only when it carries the stamp line and the agent, prompt hash, and model lines and one well formed file or artifact line per entry, and a stamp missing any of the four provenance fields is rejected rather than walked incomplete, and a malformed stamp line, a duplicate path across file and artifact lines, an artifact line whose derivation names a path the stamp does not carry, and a file or artifact line whose digest is neither sixty-four lowercase hex characters nor, for a deleted file only, the word none are each refused with an error that names the source and the defect.

BB-6. A current state document parses only as file lines each naming one path and one digest of sixty-four lowercase hex characters, and a duplicate path, a line that matches no form, or a digest of any other shape is refused with an error that names the source and the defect, and a current state may carry paths the stamp does not name and may omit paths the stamp names, because both are facts the walk reports rather than defects in the state.

BB-7. The recall walk starts from one stamped file named on the command line, and a start name that is not a file entry in the stamp is refused with an error that names the start and the defect, and the walk lists every artifact reachable from that file through derivation links, following links through artifacts as well as from the file itself, and an artifact reachable through the stamp graph but missing from the walk is a defect, and the walk lists artifacts only and never lists the start file itself.

BB-8. Every artifact in a recall result appears exactly once and carries exactly one reversibility class, the class its stamp line records, and the result is sorted first by class in the order reversible, reversible-with-compensation, and irreversible, and then by path within one class, and an artifact printed with no class or with a class its stamp line does not record is a defect.

BB-9. Every artifact line in a recall result names the artifact, its reversibility class, its status, and the chain of derivation from the start file, written as the start file and each artifact on the path in order, separated by the arrow marker, and the chain is a shortest derivation path from the start file to that artifact, and where two shortest paths exist the chain printed is the one whose sequence of paths is lexicographically smallest, and a chain naming a path that is not on a real derivation path from the start file is a defect.

BB-10. The status of an artifact in a recall result is current when the current state carries the artifact with the digest its stamp line records, drifted when the current state carries the artifact with a different digest, and missing when the current state does not carry the artifact at all, and the walk reports the status it finds and never repairs a drifted artifact, never restores a missing one, and never executes a recall as a side effect of walking.

BB-11. The stamp command and the recall command write only to the standard output and never modify the run record, the stamp, the current state, or any file in the repo they describe, and the standard output of each command is the document it was asked for and nothing else.

BB-12. Running the stamp command twice over the same run record produces byte identical stamps, and running the recall command twice over the same stamp, current state, and start file produces byte identical results, and neither output depends on the order of file entries, artifact entries, derivation parents, or current state lines in the input documents.

BB-13. The command line tool exits with code 0 when a stamp or a recall result is produced and with code 2 when any input is malformed or a file cannot be read, and a refusal prints one error line to the error stream and never a traceback, and a recall whose start file has no downstream artifacts prints the header line alone and still exits with code 0.

BB-14. The graph checks in this tool are iterative rather than recursive, so a run record whose derivation chain is thousands of artifacts deep parses and stamps in any entry order, and a derivation cycle at any depth is refused with the chain named, and no valid record ever surfaces a recursion failure.

BB-15. A line in every input format ends at a newline character and at nothing else, so a carriage return, a form feed, or any other control character inside a content line is content and is digested as recorded, and because the word that closes a content block must read exactly end with nothing after it, a record written with carriage return and newline line endings does not terminate its blocks and is refused as malformed rather than silently reinterpreted.

## Round 2 obligations

Round 2 adopts the first of the two decision points the roadmap names, the proposed classification, and adopts it offline. Where the stamp data bounds no class for an artifact, a recorded judgment may propose one of the three reversibility classes for that artifact, and the proposal is marked as proposed wherever the walk output shows it and never becomes the recorded class. The second point the roadmap names, ranking candidate compensations when a recall moves from the walk to an execution plan, is not adopted in this round and remains future work for a round that builds an execution plan surface. No live model is called in this round and no test calls the network. Answers come from recorded fixture pairs played back through a fixture player, and every committed fixture is synthetic and built for this repo. The committed fixtures record a trusted proposal for each of the three classes, one abstention, and one answer at confidence 0.45, which falls below the trust threshold this round sets.

BB-16. Amendment to BB-2 and BB-5. The word unclassed may stand in the class position of an artifact entry in a run record and of an artifact line in a stamp, and it records that the stamp data bounds no class for that artifact. The word is not a fourth reversibility class, and the three classes and their order are unchanged. A class word that is neither one of the three named classes nor unclassed is refused exactly as BB-2 and BB-5 already refuse it, and an artifact entry that names no class at all is refused as BB-2 already refuses it. Stamping carries the marker through unchanged, so the stamp for a record with an unclassed artifact prints unclassed in the class position of that artifact line, and the stamp command asks for no judgment and the marker reaches the recall as recorded.

BB-17. A classification request is built for one unclassed artifact from the stamp and the walk and from nothing else. The request carries exactly four fields. The field artifact names the artifact path. The field parents names the derivation parents the stamp records for the artifact, sorted by path. The field digest names the digest the stamp line records for the artifact. The field status names the status the walk computes for the artifact against the current state under BB-10. The judgment point is named classification, and the labels a classification answer may choose among are exactly the three reversibility classes, reversible and reversible-with-compensation and irreversible.

BB-18. A fixture is one JSON file that pairs one classification request with one response and marks itself synthetic. A choice response carries exactly the fields kind and choice and confidence and probabilities, with kind naming choice, with choice naming one of the three classes, with confidence a number between 0 and 1, and with probabilities carrying a number between 0 and 1 for each of the three classes and no other label, the three numbers adding up to 1. An abstention response carries exactly the field kind, with kind naming abstention, and carries no choice and no score and no confidence. A fixture that breaks this shape in its envelope or its request or its response is refused when the player loads it, with a judgment error that names the file and the defect, and two fixtures that pair the same request are refused at load as an ambiguous recording. A test validates every committed fixture against this same shape, so a recorded answer that changes shape fails in the suite rather than in a recall.

BB-19. The fixture player answers a classification request only from a recorded fixture whose request matches the request exactly, compared as canonical JSON with sorted keys, and where no recorded fixture matches it returns no answer, and the player reads only the directory it is given and never opens a network connection. The walk checks an answer from any source against the recorded response shape for the classification point before it trusts the answer, and an answer outside that shape, carrying a field the shape does not carry or missing a field it does or naming a label outside the three classes, counts as no judgment at all.

BB-20. An answer counts as a judgment only when it is well formed for the classification point and its confidence reaches 0.6. An answer below that confidence and an abstention and a malformed answer and the absence of any judgment source are all treated the same way, as no judgment at all, and in every one of those cases the walk behaves exactly as it behaved before the seam existed.

BB-21. The recall command accepts an optional fixtures flag naming a fixtures directory, and a directory that cannot be loaded prints one error line and exits with code 2 and shows no traceback. The walk asks for a judgment only about an unclassed artifact it would list, once per such artifact, and an unclassed artifact the walk does not reach is never asked about and never refuses the walk. Where no trusted judgment proposes a class for an unclassed artifact the walk would list, the recall is refused with the same error line the stamp parser gives for a class word outside the three named classes, naming the source and the artifact, and where more than one such artifact lacks a trusted proposal the refusal names the first of them in path order, and the command exits with code 2 and prints that one line and no traceback. Where a trusted judgment proposes a class, the artifact appears in the result carrying the proposed class, printed as the class word followed by the word proposed, then its status and its chain as BB-9 and BB-10 state them, and it is sorted into the group of its proposed class under the order BB-8 states, amending BB-8 for this case alone. A proposed class is never written back into the stamp or into any file, and BB-11 stands over the seam unchanged. An artifact whose stamp line records a class is never asked about and is never re-proposed, and its result line is byte identical to the line the walk printed before the seam existed, and a walk over a stamp with no unclassed artifact it would list makes no requests at all and prints byte identical output with and without the flag.

BB-22. Amendment, added by the Round 2 review. Three precision fixes to BB-18 and BB-19. First, the three probabilities of a choice response add up to 1 within a tolerance of one thousandth, because decimal probability values rarely sum to exactly 1 in binary floating point arithmetic, and a response whose probabilities sum outside that band is refused at load and counts as no judgment from any source. Second, the fixture envelope carries exactly the fields synthetic, judgment_point, request, and response, and a fixture carrying any other top level field is refused at load naming the field. Third, a response kind that is not a string is a malformed answer, refused at load and counted as no judgment from any source, and a numeric field whose value cannot be converted to a finite float, however it was written in the JSON text, is not a number for the unit interval checks and is refused or counted as no judgment on the same terms.

## Round 3 obligations

Round 3 adopts no new decision point and changes no behaviour the earlier rounds promised. It completes the hardening of the judgment seam Round 2 built, carrying one precision rule the Round 2 review applied to the fixture envelope through to the response check as well, and it writes into the contract two readings of the stamp format and one reading of the fixture format that the earlier rounds applied without naming them. No live model is called in this round and no test calls the network, and every fixture the round adds is synthetic and built for this repo.

BB-23. Amendment, added in Round 3. Three precision rules. First, where validation names a field that an answer or a fixture carries and its shape does not, the field named is the first of the extra fields ordered by their printed form, in the check of a response as in the check of the fixture envelope, and an answer whose extra fields carry keys that cannot be ordered against one another, keys of mixed types among them, is malformed on the same terms and counts as no judgment, so the recall walk driven by a source that hands back such an answer behaves exactly as it behaves with no source at all. Second, two readings of the stamp format stand recorded. A stamp whose derivation lines form a cycle is admitted, because the refusal list of BB-5 does not name a cycle among the defects of a stamp, and the recall walk terminates on such a stamp and reports the artifacts it reaches in the order BB-8 and BB-9 state. And the stamp parser admits a file line for a deleted file carrying a digest of sixty-four lowercase hex characters where the stamp printer writes the word none, and the digest is kept as recorded, while a stamp the tool itself prints always writes none on a deleted file line. Third, a fixture file whose JSON text gives one field twice is judged on the last value the text gives that field, because the parser that reads the text resolves a duplicated field before validation sees the object, and the fixture is admitted or refused on the terms of that last value.

## Round 4 obligations

Round 4 builds the execution plan surface the roadmap names and adopts the second of the two decision points, the ranking of candidate compensations for one artifact, and adopts it offline on the terms Round 2 adopted the first. The plan is a document a human reviewer reads before any recall is executed, and it executes nothing and approves nothing and triggers nothing, and executing a recall remains a separate reviewed act that no model and no command in this tool performs. A compensation ranking orders the options the reviewer sees, and it never becomes an instruction to perform one and never silently becomes a recorded fact about the artifact. No live model is called in this round and no test calls the network. Answers come from recorded fixture pairs played back through the fixture player, and every committed fixture is synthetic and built for this repo. The committed classification fixtures stand in the fixtures directory exactly as Round 2 left them, and the committed ranking fixtures stand in a second directory named fixtures-ranking, and one fixtures directory handed to a command may carry pairs for both points, each point answering only its own requests.

BB-24. The plan command takes the same recorded inputs as the recall command, a stamp and a current state and one stamped file to start from, and prints a plan document for the downstream artifacts of that file. The plan runs the same walk the recall command runs, so an unclassed artifact the walk would list is proposed a class or refused on exactly the terms BB-21 states, and the artifacts appear in the order BB-8 states. The document opens with a header line that names the word plan and the start file. Under the header, each artifact the walk lists prints the artifact line the recall document prints for it under BB-9 and BB-21, naming the artifact and its class with the proposed marker where the walk carries one and its status and its chain, and under each artifact line the plan prints one compensation line per candidate compensation the artifact carries under BB-25, or the single line BB-25 states for an artifact that carries none. A walk that lists no artifacts produces the header line alone and still exits with code 0. The plan command writes only to the standard output and never modifies the stamp, the current state, or any file in the repo it describes, and it exits with code 0 when a plan is produced and with code 2 when any input is malformed or a file cannot be read, and a refusal prints one error line to the error stream and never a traceback, on the terms BB-11 and BB-13 state for the other commands.

BB-25. The candidate compensations are three named forms, rebuild-from-parents and remove-artifact and quarantine-artifact, and the set an artifact carries is a function of its class and its status and of nothing else, and the class an artifact carries for this rule is the class the walk result carries, so an artifact standing under a proposed class takes the set of its proposed class. An artifact whose status is current and whose class is reversible carries rebuild-from-parents and then remove-artifact. An artifact whose status is current and whose class is reversible-with-compensation carries all three in the order named above. An artifact whose status is current and whose class is irreversible carries quarantine-artifact alone, because no candidate restores such an artifact and containment is the only honest entry. An artifact whose status is drifted carries quarantine-artifact and then remove-artifact, whatever its class, because rebuilding would overwrite work the stamp never recorded. An artifact whose status is missing carries no candidate, and its one compensation line reads compensation none required, the artifact is already absent. The order a set is stated in here is the order the plan prints when no trusted ranking orders it, and that order is named the canonical order of the set. A class word outside the three the records name defines no candidate set, and asking for its set refuses, a case the walk never presents because it refuses or proposes every unclassed artifact before the plan reads a class.

BB-26. A ranking request is built for one candidate compensation of one artifact from the stamp and the walk and from nothing else. The request carries exactly five fields. The field artifact names the artifact path. The field candidate names the candidate compensation, one of the three forms BB-25 names. The field class names the class the artifact carries in the walk result, which for a proposed artifact is its proposed class. The field status names the status the walk computes for the artifact against the current state under BB-10. The field chain names the chain the walk prints for the artifact, written as the start file and each artifact on the path in order, separated by the arrow marker. The judgment point is named compensation-ranking. The plan builds one ranking request per candidate for an artifact that carries two or more candidates, and it builds no ranking request for an artifact that carries fewer than two candidates.

BB-27. A ranking fixture is one JSON file that pairs one ranking request with one response and marks itself synthetic. The fixture envelope carries exactly the fields synthetic, judgment_point, request, and response, and a fixture carrying any other top level field is refused at load naming the field, and judgment_point names compensation-ranking. A score response carries exactly the fields kind and score and confidence, with kind naming score, with score a number between 0 and 1 that rates how completely the candidate compensation restores the prior state, and with confidence a number between 0 and 1. An abstention response carries exactly the field kind, with kind naming abstention, and carries no score and no confidence. A fixture that breaks this shape in its envelope or its request or its response is refused when the player loads it, with a judgment error that names the file and the defect, and two fixtures that pair the same request for the same judgment point are refused at load as an ambiguous recording. A test validates every committed ranking fixture against this same shape, so a recorded answer that changes shape fails in the suite rather than in a plan. The fixture player answers a ranking request only from a recorded fixture whose request matches the request exactly, compared as canonical JSON with sorted keys, and where no recorded fixture matches it returns no answer, and the player reads only the directory it is given and never opens a network connection. The precision rules of BB-22 and BB-23 stand over ranking fixtures and ranking answers in the same terms they state for the classification point, so a response kind that is not a string is a malformed answer, and a numeric field whose value cannot be converted to a finite float is not a number for the unit interval checks, and where validation names an extra field the field named is the first of the extra fields ordered by their printed form. A directory of fixtures may carry pairs for both judgment points, and the player loads each pair under its own point and answers each point only from its own pairs, so the recall command answers exactly as it answered before this round from any directory it is handed.

BB-28. The plan checks an answer from any source against the recorded response shape for the ranking point before it trusts the answer, and an answer outside that shape, carrying a field the shape does not carry or missing a field it does, counts as no judgment at all. A score answer counts as a judgment only when it is well formed for the ranking point and its confidence reaches 0.6, and an answer below that confidence and an abstention and a malformed answer and the absence of any judgment source are all treated the same way, as no judgment at all. Where trusted scores order an artifact, the candidates a trusted score covers print first, ordered by their scores from highest to lowest, with candidates whose trusted scores are equal keeping their canonical order among themselves, and the candidates no trusted score covers print after them in their canonical order. A candidate a trusted score covers prints its compensation line with the score written after the candidate name as the word score followed by the shortest decimal form that round trips to the recorded value, with a score of negative zero written as 0.0, and a candidate no trusted score covers prints its compensation line with the candidate name alone. Where no trusted score covers an artifact, its compensation lines print in canonical order and carry no score, exactly as the plan prints them with no judgment source at all, and a plan built with a judgment source that abstains on every ranking request is byte identical to the plan built with no judgment source.

BB-29. The plan command accepts an optional fixtures flag naming a fixtures directory, and a directory that cannot be loaded prints one error line and exits with code 2 and shows no traceback, on the terms BB-21 states for the recall command. The plan asks for classification judgments through the same fixture player and on the same terms as the recall command, and it asks for ranking judgments only inside the plan, and the recall command never builds a ranking request and never asks one. A ranking is never written back into the stamp or into any file, and a proposed class in a plan is never written back either, and BB-11 stands over the plan unchanged.

## Round 5 obligations

Round 5 rebuilds the tool as a Rust crate. The Python implementation the earlier rounds landed is the behavioural specification for the port, and it is removed inside this slice once the port matches it, and nothing in this round adds a feature or changes a promised behaviour. The crate reads no input the Python tool did not read and writes no file at all, as BB-11 has always promised. The boundary of the tool stands exactly where it has always stood. Badbatch stamps what a run left behind and never records the run itself, and the port changes nothing about that boundary.

Two of this round's readings rest on probes of the oracle's own behaviour, and the findings stand here so the obligations below can be told apart from assumed rules. For the fixture reader, documents nested in arrays and in objects were fed to the oracle through a real fixtures directory at depths either side of the boundary the reader keeps. A document nested 9991 containers deep loads and is then refused as a document, and one nested 9992 deep raises the recursion error the oracle never catches, and the boundary is the same for both carriers. An integer literal of 4300 digits converts and is refused as a value, and one of 4301 digits raises the integer conversion error the oracle never catches, and the sign of a negative literal is not counted toward the limit, and a multi digit literal written with a leading zero is refused as grammar and not as the limit. For the argument parser, the oracle's assignment was read as an in-process namespace table over every token shape up to five tokens drawn from values and separators and the fixtures option pair. The table shows the distribution running per segment, with a segment ending at each flag the parser consumes, and it shows an option pair standing between two values changing the segmentation and so changing which slot receives a string and which receives a list, and that reading corrects the single run reading the round's early probes assumed. A trailing separator that closes a segment holding no positional, in a stream where a flag was consumed earlier, refuses on the oracle even when every slot is filled, and the same streams without the separator or with a positional in the closing segment run.

BB-30. The tool is a Rust library crate with one binary. The crate anyhow 1 is confined to the binary entry. No shipped code reads or writes JSON through an external crate, and serde_json appears if at all only as a dev dependency of the corpus tests. Cargo tests are the only committed test suite, and no Python product file, test file, or packaging file remains tracked when the slice lands.

BB-31. The obligations BB-1 through BB-29 stand unchanged, and the ported corpus covers the Python suite test for test in substance. The committed examples print byte for byte as the Python tool printed them, and the committed fixtures in the fixtures directory and the fixtures-ranking directory load and answer exactly as they did, and one fixtures directory may carry pairs for both judgment points and answers each point only from its own pairs, as BB-27 states.

BB-32. The setup invariants stand in crate form. The stub obligations BB-S1 through BB-S5 stand verbatim with their word counts and their prefix and numbering, and the canonical agents prefix keeps the digest the setup test pins. The README round count pin keeps the findall form the Python test used and reads the closed count at the value the slice carries. The dash scan covers files ending .md, .yml, .yaml, .rs, .toml, .txt, .json, .jsonl, and .lock, with .rs standing where .py stood, and extensionless files, and it asserts named anchor files were scanned, and it skips directories named .git, target, .pytest_cache, and __pycache__ at any depth and .venv, venv, node_modules, and .tox at the root.

BB-33. The text model of BB-15 stands stated for the crate. Meaningful lines are found by splitting the text on the newline character alone and on no other boundary. Word splitting and edge trimming follow the whitespace table of the oracle runtime, whose ranges are 9 to 13, 28 to 32, 133, 160, 5760, 8192 to 8202, 8232 and 8233, 8239, 8287, and 12288. Content block lines are raw lines, and a content block ends only at a raw line reading exactly the word end, and a record whose content block never ends is refused on the terms BB-2 states.

BB-34. The fixture reader is the crate's own JSON reader, and it speaks the language the oracle reader speaks. An object field given twice keeps the last value at the position of its first giving. An integer is exact at any length up to the digit limit. The literals the oracle reads as non finite values, and an exponent that overflows, read as those same values and fail the number checks on the same terms. A string escape naming a code point in the surrogate range is kept as that code point, so two strings that differ only in such a code point are two different strings and never compare equal and never answer for one another, and the printed form of such a code point in a refusal is the escaped form the oracle's printed form writes. A fixture document nested 9991 containers deep loads, and one nested 9992 deep raises the uncaught family of BB-37, and the ceiling is this crate's own probed value and not a sibling crate's. An integer literal of 4300 digits converts, and one of 4301 raises the uncaught family, and the sign of a negative literal is not counted toward the limit. A multi digit integer written with a leading zero is a grammar refusal and not the digit limit. A fixture load failure names the file with exactly the messages the oracle gives, that the file cannot be read, that it is not valid UTF-8, or that it is not valid JSON, and in each message the file is named by the folded joined path of BB-38.

BB-35. Printed forms follow the oracle. The printed form of a string chooses its quote as the oracle chooses and escapes as the oracle escapes, and whether a character prints as itself is decided by the general category table of the oracle's Unicode version, which is 15.0.0. A score in a plan prints in the shortest decimal form that round trips to the recorded value, in ordinary notation unless the decimal exponent of the value is smaller than minus 4 or is at least 16, in which case the exponent form prints with at least two exponent digits, and a whole value keeps one place after the point, and a score of negative zero is stored and printed as 0.0, as BB-28 states.

BB-36. The judgment seam stands in the crate on the terms BB-16 through BB-22 and BB-27 and BB-28 state, with the validation order those obligations and the oracle's code together fix, envelope before point before request before response, and the exact field sets per kind, and the probability sum taken in label order and compared against the tolerance of one thousandth. The trust threshold is the literal 0.6 in the crate as in the oracle, and a test pins the literal itself beside the behavioural pins at the threshold. The canonical comparison key sorts keys and uses the oracle's default separators and escapes non ASCII characters, writing an astral character as a surrogate pair.
